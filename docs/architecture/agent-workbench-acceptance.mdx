### 验收发现并修复的结束逻辑问题

第一次明确规则的调优任务 `196f0384…` 最终完成，但已保存候选后仍向模型暴露分析专用的 `finish_analysis`，错误提示又笼统要求保存工件，导致 7 次工具失败和重复保存。模型还尝试在自身结束之前查询后端尚未开始的复测。

现已在明确构建与调优任务中移除 `finish_analysis`；自动模式误用时，已保存工件会收到准确的结束提示。Codex 指令明确调优只需保存候选，冻结测试集由后端在当前轮次结束后执行。以原失败候选和相同规则重新验收，模型请求从 13 次降至 3 次，累计 token 从 122,520 降至 28,710，保存 1 个候选、工具失败 0 次，最终仍为 2/2。

新增边界测试并复跑真实源码进程契约和工作台回归，**80 项通过**（77 项适配层/工作台测试，加 3 项 Worker 启动测试），Ruff 与 diff 空白检查通过。未重新编译 Rust；`.runtime` 保持约 296 MiB，没有恢复之前清理的 Rust 中间目录。

## 2026-10-20 调优失败排查

workflow `7` 的任务 `bb256056-f5ea-4cb9-9c88-a7aa673d0349` 于本地时间 17:13:59 以 `Workbench model budget exceeded` 失败。当时网关写死 40 次请求 / 150,000 累计 token，失败记录没有保存用量，不能追溯确切累计数。Codex 两次给 `validate_candidate` 传入 `summary` 被拒；重复发送完整代码和包含重复事件的上下文增加了消耗。

同次基线的 `node_visited` 使用中文节点名，而旧评测器只比较 ID。以原候选和记录事件离线重算，原来的 `0/5` 应为 `2/5`；另外三条仍存在实际行为或文本断言失败，没有修改历史记录或放宽测试集。

## 2026-10-22 通用自动诊断与局部修复

自动构建后的修复现在使用真实运行时的逐轮证据：每条用户输入、回复、节点跳转和工具调用都关联到对应轮次。失败回复完整提供给构建模型，不再与所有通过场景平均分摊截断额度；旧评测没有轮次标记时明确保留为未定位事件，不猜测对应关系。修复输入使用原图的普通字段、冻结测试集和失败诊断，不重复发送完整 SDK 或无关历史运行记录。

文本断言失败时，诊断同时列出实际回复节点和原图中包含所需内容的节点。某轮没有跳转时，不能仅修改后续节点并声称修复了当前回复。服务端还根据失败轮次涉及的非结束节点，自动补入通用执行约束：只扮演助手、当前步骤完成不等于整个任务完成、通过已有工具切换阶段、非结束节点不提前收尾、新步骤需要确认时等待新的用户回复。原 SOP 允许自动衔接的例外仍保留。这些约束不包含客户名称、数字、费率或业务分支匹配，重复修复也不会重复插入同一约束。

模型保存修复时需提交 `repair_plan`，说明失败断言、原因、受影响节点、原节点提示词的精确引用和修改方式。服务端检查引用与失败项存在、所有修改节点有依据；自动修复保留原提示词、开场白、分支条件和分支话术，允许追加执行澄清，不允许静默删除。业务数值、节点和条件由当前 Agent 的原始内容提供，不内置到构建器。若冻结测试与原文冲突，保留候选并报告，不能修改测试或删掉原文来凑通过率。

## 只运行测试与完整资料读取

工作台增加 `test` 任务模式。自动模式先在独立临时上下文中识别当前请求；测试请求不会进入持久构建会话、历史修改任务、候选生成或自动修复循环。排队时冻结测试目标，只读测试复用相同指纹的版本，缺少版本记录时仅保存原内容的不可变测试快照，不更新草稿或发布状态。数据库拒绝测试任务调用候选修改保存接口。

完整 XLSX/CSV 在无凭据、受资源约束的解析子进程内读取，验证原文件 SHA-256。模型依据本次要求选择数据表、对话列与角色标签，程序导入所有非空行并保存文件哈希、表名、列名和物理行号。传输批次不等于样本数量上限；解析错误逐条列为无法判定，不能静默漏行。普通附件按需分页读取时，也会从原文件恢复旧的截断预览。存在多列对话且当前请求未指定时，工作台返回待补充问题；“补充并继续”携带原任务标识、资料和固定版本，而非重新从任意历史需求推断目标。

客户发言进入真实文本运行时，参考坐席发言仅用于独立语义评审。相邻同角色发言合并成一次输入，保留全部原文字句。每条实际执行记录包括运行编号、逐轮回复、节点事件、工具记录和模型使用量；评审通过原文行号与实际回复轮次引用，引用文字由服务端取回，避免模型改写证据。固定脚本中断、运行异常、未执行样本与评审不确定分别记录；任务执行完成不代表全部测试通过，也不等于任意真实通话的质量保证。

工作台展示逐轮执行/评审进度、整个任务汇总、每批结果及原文对照。测试结果卡不显示新候选或自动修改入口。新增逐轮事件只增量更新进度，不触发每轮重新下载整个结果历史。验收需核对每条运行编号、完整来源行集合与前后草稿指纹，不使用模型声称“已执行”作为证据。

中断或异常测试可以从工作台继续：保留原任务要求、附件和固定版本，校验运行模型配置指纹及逐条测试内容后，复用已完成且有实际回复的结果；运行错误和未执行用例重新执行。只有评审中断时，使用原实际对话补齐评审，不重复调用 Agent；已有完整评审但结论为证据不足或脚本错位的用例保持原结论。复用记录保留原运行编号和原评测 ID，汇总明确标示复用数量；补评同时保留原评审错误。配置变化时拒绝混合结果，原测试和原始失败记录保留。

多次恢复沿原任务链寻找有效结果；同一要求、附件 ID 和文件哈希的已确认表格映射直接复用，不再调用模型重新选择测试列。流式连接的空包和心跳不算有效模型进展，连续无有效输出时触发 I/O 超时；持续产生实际输出时不施加整项任务时间预算。重复提交同一份无效结构化结果会结束该条评审并保留无法判定原因，不拖住整个批次。

后续分析通过只读 `read_evaluation` 读取仿真结果，不能用普通 Agent Runs 替代。任务上下文提供真实结果索引，历史助手结论不作为凭据。最终分析涉及具体运行编号时，服务端会重新绑定实际对话、原文引用和被测版本规则，独立检查结论；没有证据的确定性断言必须修订。此检查不能把模型评审当成事实，也不能为通过测试而修改 SOP。结构化识别/评审取得有效工具回执后直接结束该步骤，避免为了生成一句结束语继续重复调用模型。
